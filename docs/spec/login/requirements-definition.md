# ログイン画面 要件定義

## 1. 画面情報

- 画面名: ログイン画面
- feature 名: `auth`
- route: `/login`
- 関連画面: `/dashboard`, `/signup`
- ステータス: Draft
- 作成日: 2026-03-29
- 更新日: 2026-03-29

## 2. 目的とスコープ

### 2-1. 目的

- 登録済みユーザーがメールアドレスとパスワードで認証し、アプリの利用を開始できるようにする
- 未認証ユーザーを保護画面からログインフローへ戻し、認証完了後に業務画面へ接続する入口とする

### 2-2. スコープ

- この画面で提供する機能:
  - メールアドレス、パスワードの入力
  - クライアントサイドバリデーション
  - `POST /auth/login` による認証
  - 認証エラーの画面内表示
  - ログイン成功後の画面遷移
  - 会員登録画面への導線
- この画面では扱わない機能:
  - パスワード再発行
  - ソーシャルログイン
  - 多要素認証
  - ログイン履歴確認
  - CAPTCHA やアカウントロック

## 3. 対象ユーザーと利用条件

- 想定ユーザー:
  - 登録済みの一般ユーザー
  - 保護画面へアクセスして未認証扱いとなったユーザー
- 認証要件:
  - 未認証状態で利用することを主目的とする
  - 認証済みユーザーが `/login` に直接到達した場合も画面表示を許容する
- 到達経路:
  - URL 直接入力
  - `AuthGuard` による保護画面からのリダイレクト
  - 会員登録画面からの遷移

## 4. 前提条件と依存

- 関連 feature:
  - `auth`
  - `dashboard`
  - 保護画面 feature 全般
- 関連 API:
  - `POST /auth/login`
  - `GET /auth/check`（route guard で利用する場合）
- 前提データ:
  - 初期表示に必要なサーバデータはない
  - 認証成功時はアクセストークンを受け取る
- 外部サービス依存:
  - なし
- レイアウト制約:
  - `AuthScreenLayout` を使った全画面高の認証レイアウト
  - モバイル優先の 1 カラム構成
  - 白ベース、緑アクセント、中央寄せカード

## 5. ユーザーストーリー

- ユーザーとして、業務画面を利用するために登録済みの認証情報でログインしたい
- ユーザーとして、入力ミスや認証失敗の理由を画面上で把握したい
- ユーザーとして、アカウント未作成の場合に会員登録画面へ迷わず移動したい
- ユーザーとして、保護画面からログインへ遷移した場合は認証後に元の目的地へ戻りたい

## 6. 画面概要

### 6-1. 画面構成

- ヘッダー:
  - グローバルヘッダーは表示しない
  - カード内に画面タイトルと説明文を表示する
- メインコンテンツ:
  - メールアドレス入力
  - パスワード入力
  - 認証エラーメッセージ
  - ログインボタン
  - 会員登録ボタン
- 補助領域:
  - 背景グラデーション
  - `.page-shell` による左右余白と中央寄せ
- フッター:
  - なし
- モーダル / ドロワー:
  - なし

### 6-2. 主要アクション

- 初期表示時に行うこと:
  - 空のフォームを表示する
  - route state に `AuthGuard` から渡された遷移元情報がある場合は認証後遷移先として扱う
- ユーザー操作:
  - メールアドレスとパスワードを入力する
  - Enter またはボタン押下でログイン送信する
  - 会員登録ボタンから `/signup` へ遷移する
- 操作結果:
  - 成功時は認証情報を保持して次画面へ遷移する
  - 失敗時は入力エラーまたは認証エラーを画面内に表示する

## 7. ユーザーフロー

1. ユーザーが `/login` に到達する
2. 画面はタイトル、説明文、入力フォーム、アクションを表示する
3. ユーザーがメールアドレスとパスワードを入力する
4. 入力不備がある場合は該当項目直下にエラーを表示する
5. ユーザーがログイン操作を行うと `POST /auth/login` を実行する
6. 成功時はトークンを保持し、遷移元があればその画面、なければ `/dashboard` へ遷移する
7. 失敗時はフォーム下部に認証エラーを表示し、再入力を受け付ける

## 8. 機能要件

### 8-1. 初期表示

- 初期表示時に必要な API / データ取得:
  - 画面自体では不要
  - ただし route guard 適用時は `GET /auth/check` による認証確認が先行する
- 初期表示時の UI:
  - タイトル `ログイン`
  - 説明文 `メールアドレスとパスワードを入力してログインしてください。`
  - メールアドレス入力
  - パスワード入力
  - プライマリアクション `ログイン`
  - セカンダリアクション `会員登録`
- 権限不足 / 未認証時の扱い:
  - 未認証ユーザーは画面利用可
  - 保護画面から来た場合はこの画面で再認証を行う

### 8-2. 入力 / 操作

- 入力項目:
  - メールアドレス
  - パスワード
- 操作可能なボタン / リンク:
  - `ログイン`
  - `会員登録`
- 活性 / 非活性条件:
  - 通常時は両ボタン活性
  - ログイン送信中は両ボタン非活性
- 二重送信防止:
  - mutation 実行中はプライマリボタンをローディング表示にし、再送信を防止する

### 8-3. 出力 / 表示

- 入力項目のラベルは常時表示する
- バリデーションエラーは各入力項目の直下に表示する
- API エラーはフォーム下部のアラートとして表示する
- ボタン文言:
  - 通常時: `ログイン`
  - 送信中: `送信中...`

## 9. 状態要件

- Loading:
  - ログイン送信中に表示する
  - `ログイン` ボタンをローディング状態にする
  - `ログイン` / `会員登録` を操作不能にする
- Empty:
  - データ一覧の empty 状態は存在しない
  - 初期状態は空フォーム表示とする
- Success:
  - 成功メッセージは画面内に残さず遷移を優先する
  - 遷移先は `AuthGuard` から渡された `location.state.from` の内部ルートを優先し、未指定や不正値は `/dashboard` とする
- Validation Error:
  - 各入力欄の直下に表示する
  - メッセージは日本語で具体的に示す
- API Error:
  - フォーム下部に `role="alert"` のアラートを表示する
  - 入力内容は保持し、修正または再送信を可能にする
- Unauthorized:
  - ログイン API の `401` は画面内エラーとして扱う
  - 保護画面で `401` が発生した場合は `AuthGuard` 経由で `/login` に遷移する

## 10. バリデーションと業務ルール

- 必須項目:
  - メールアドレス
  - パスワード
- フォーマット制約:
  - メールアドレスは email 形式
- 相関チェック:
  - なし
- 業務上の入力制約:
  - パスワード文字数や複雑性はログイン画面では判定しない
  - 未確認メールや停止アカウントの扱いはサーバレスポンスに従う
- 操作可能条件:
  - 送信中以外は再送信可能

## 11. API / データ要件

### 11-1. 利用 API 一覧

| 用途     | Method | Endpoint      | 入力                | 出力                                                                 | 備考                           |
| -------- | ------ | ------------- | ------------------- | -------------------------------------------------------------------- | ------------------------------ |
| ログイン | POST   | `/auth/login` | `email`, `password` | `accessToken` または `access_token`, `tokenType` または `token_type` | 送信時に認証ヘッダは付与しない |
| 認証確認 | GET    | `/auth/check` | なし                | なし                                                                 | route guard で利用する場合のみ |

### 11-2. データ要件

- 画面表示に必要なデータ項目:
  - メールアドレス
  - パスワード
  - 認証エラーメッセージ
- フロントで加工が必要な項目:
  - ログイン API のトークンキー差異を吸収する
  - route state の `from` は内部ルートだけを採用し、外部 URL や不正値は `/dashboard` にフォールバックする
- 欠損時のフォールバック方針:
  - トークン欠損時は認証情報を保持せず、エラー扱いとする
  - 遷移元が不明な場合は `/dashboard` を既定遷移先とする

## 12. UI / UX 要件

- モバイル優先で成立すること
- 600px 未満では 1 カラム、左右 16px 以上の余白で表示すること
- 600px 以上ではカード幅を拡張しても 1 カラム構成を維持すること
- 960px 以上では上下余白を十分に確保し、カードを画面中央に固定すること
- 主要 CTA はファーストビュー内に収めること
- 認証エラーが表示されてもフォーム全体の可読性を損なわないこと

## 13. アクセシビリティ要件

- ラベルは常時表示し、入力要素と関連付ける
- キーボードだけでメール入力、パスワード入力、送信、会員登録遷移を完結できる
- フォーカス順は上から下へ自然であること
- エラーメッセージは入力直下またはアラート領域に表示し、読み上げ可能にする
- `aria-invalid`, `aria-describedby`, `role="alert"`, `aria-live="polite"` を適切に利用する
- コントラストは WCAG AA を満たす

## 14. 非機能要件

- 想定表示件数:
  - 一覧表示なし
- パフォーマンス上の注意:
  - 初期表示で不要な API 呼び出しを行わない
  - 認証成功後は不要な再描画を増やさず即時遷移する
- 監視 / ログ出力の要件:
  - パスワードやアクセストークンをログ出力しない
  - 失敗時は必要最小限のエラー情報のみ扱う
- セキュリティ上の注意:
  - ログイン API 送信時は認証ヘッダを付与しない
  - 受け取ったトークンはメモリ上で保持する
  - ブラウザ永続保存を前提にしない

## 15. 対象外

- パスワードを忘れた場合の復旧導線
- MFA やワンタイムコード入力
- 外部 ID プロバイダ連携
- サインアップ後のメール未確認ユーザー向け専用導線

## 16. Definition of Done

- メールアドレスとパスワードでログインできる
- バリデーションエラーと API エラーの表示仕様が明確である
- 送信中の二重送信防止仕様が定義されている
- ログイン成功後の遷移先優先順位が明確である
- モバイル / デスクトップのレイアウト要件が定義されている
- アクセシビリティ観点とテスト観点が洗い出されている
