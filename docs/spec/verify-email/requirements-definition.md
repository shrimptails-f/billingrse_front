# メール認証画面 要件定義

## 1. 画面情報

- 画面名: メール認証画面
- feature 名: `auth`
- route: `/signup/verify?token=<verification-token>`
- 関連画面: `/signup`, `/signup/email-sent`, `/signup/email-resend`, `/login`, `/dashboard`
- 作成日: 2026-03-29
- 更新日: 2026-03-29

## 2. 目的とスコープ

### 2-1. 目的

- 会員登録後にユーザーがメール内リンクからメールアドレス認証を完了できるようにする
- 認証結果を 1 画面で明示し、次に取るべき行動を迷わず選べるようにする

### 2-2. スコープ

- この画面で提供する機能:
  - query parameter `token` の受け取り
  - 初期表示時の自動メール認証実行
  - 認証中 / 成功 / 失敗 / トークン欠損の状態表示
  - 確認メール再送画面、会員登録画面、ログイン画面、ダッシュボードへの導線表示
  - 認証成功後の URL からのトークン除去
- この画面では扱わない機能:
  - トークンの手入力
  - 認証成功後の自動ログイン
  - 確認メール再送フォームそのものの入力仕様
  - トークン期限切れや再送上限の詳細説明

## 3. 対象ユーザーと利用条件

- 想定ユーザー:
  - 会員登録直後に確認メールを受け取った未認証ユーザー
  - 確認メールのリンクを後から再度開いたユーザー
  - トークン不備や期限切れで再送が必要になったユーザー
- 認証要件:
  - 画面自体は未ログインで利用可能とする
  - 認証 API 呼び出しでは認証ヘッダや既存セッションを前提にしない
  - 成功後に `ダッシュボードへ移動する` を選んだ場合、未ログインなら `AuthGuard` により `/login` へ遷移する
- 到達経路:
  - 確認メール内リンクからの直接アクセス
  - `/signup/email-sent` からの案内に従った再アクセス
  - URL 直接入力やブックマークによる再訪

## 4. 前提条件と依存

- 関連 feature:
  - `auth`
  - `dashboard`
- 関連 API:
  - `POST /auth/email/verify`
  - `POST /auth/email/resend`（失敗時の次アクション先として依存）
- 前提データ:
  - メール認証に必要な `token` を query parameter で受け取る
- 外部サービス依存:
  - 確認メール配信基盤
- レイアウト制約:
  - `AuthScreenLayout` を使った認証系の共通レイアウト
  - モバイル優先の 1 カラム構成
  - 白ベース、緑アクセント、中央寄せカード

## 5. ユーザーストーリー

- ユーザーとして、会員登録を有効化するためにメール内リンクを開いて認証を完了したい
- ユーザーとして、認証に失敗した理由を画面で把握し、すぐ再送や再登録へ進みたい
- ユーザーとして、認証完了後にログインまたは業務画面へ進む導線を見失いたくない

## 6. 画面概要

### 6-1. 画面構成

- ヘッダー:
  - グローバルヘッダーは表示しない
  - カード内に状態ラベル、タイトル、説明文を表示する
- メインコンテンツ:
  - 認証状態を示すスピナーまたはステータスアイコン
  - 状態メッセージ
  - 状態に応じた遷移ボタン群
- 補助領域:
  - 背景グラデーション
  - `.page-shell` による左右余白と中央寄せ
- フッター:
  - なし
- モーダル / ドロワー:
  - なし

### 6-2. 主要アクション

- 初期表示時に行うこと:
  - query parameter から `token` を読む
  - `token` があれば一度だけ `POST /auth/email/verify` を実行する
  - `token` がなければ API 呼び出しを行わず欠損状態を表示する
- ユーザー操作:
  - `ダッシュボードへ移動する`
  - `ログイン画面へ進む`
  - `確認メールを再送する`
  - `会員登録に戻る`
- 操作結果:
  - 成功時は成功文言を表示し、トークンを URL から除去する
  - 失敗時または欠損時は再送と代替導線を提示する

## 7. ユーザーフロー

1. ユーザーが確認メール内リンクから `/signup/verify?token=...` に到達する
2. 画面は認証中の説明とスピナーを表示する
3. `POST /auth/email/verify` を 1 回実行する
4. 成功時は成功状態へ切り替え、URL から `token` を除去する
5. ユーザーはダッシュボードまたはログイン画面へ進む
6. 失敗時はエラー状態へ切り替え、確認メール再送または会員登録へ戻る
7. `token` なしで到達した場合は欠損状態を即時表示し、再送やログインへの導線を出す

## 8. 機能要件

### 8-1. 初期表示

- 初期表示時に必要な API / データ取得:
  - `token` がある場合のみ `POST /auth/email/verify`
- 初期表示時の UI:
  - 状態ラベル `メール認証`
  - 状態別タイトルと説明文
  - 認証中はスピナーと待機文言
- 権限不足 / 未認証時の扱い:
  - 画面自体は公開し、未認証でも閲覧可能とする
  - `ダッシュボードへ移動する` のクリック後は保護画面側の guard に従う

### 8-2. 入力 / 操作

- 入力項目:
  - なし
- 操作可能なボタン / リンク:
  - 成功時:
    - `ダッシュボードへ移動する`
    - `ログイン画面へ進む`
  - 失敗時 / 欠損時:
    - `確認メールを再送する`
    - `会員登録に戻る`
    - `ログイン画面へ戻る`
- 活性 / 非活性条件:
  - 認証中は遷移ボタンを表示しない
  - 成功または失敗状態になったら表示中のボタンを活性化する
- 二重送信防止:
  - 同一 `token` に対する認証 API は 1 度だけ実行する

### 8-3. 出力 / 表示

- 状態別のタイトルと説明文をカード上部に表示する
- 状態メッセージは中央のステータスパネル内に表示する
- 認証中と結果表示は `aria-live="polite"` で読み上げ可能にする
- 成功時は緑系、失敗時は赤系の視覚差を付ける
- エラー文言:
  - `invalid_token` の場合は `不正なトークンです。`
  - その他は `エラーが発生しました。時間をおいて再度お試しください。`

## 9. 状態要件

- Loading:
  - `token` ありで認証 API 実行中に表示する
  - スピナーと `メールアドレスを確認しています...` を表示する
  - 次アクションボタンは表示しない
- Empty:
  - 一覧やデータ 0 件の概念はない
  - empty 状態は持たない
- Success:
  - `メール認証が完了しました` を表示する
  - 成功メッセージと次アクションを提示する
  - 自動遷移は行わない
- Validation Error:
  - フォームがないため入力バリデーションは発生しない
  - `token` 欠損は `missing` 状態として扱う
- API Error:
  - エラー状態として結果パネル内に表示する
  - 同画面での再試行ボタンは持たず、再送画面への導線で回復させる
- Unauthorized:
  - 公開画面のため `/signup/verify` 自体ではリダイレクトしない
  - verify API の `401` は汎用エラーとして扱う

## 10. バリデーションと業務ルール

- 必須項目:
  - `token` query parameter（メール認証フローを成立させるため）
- フォーマット制約:
  - `token` は文字列として扱い、画面側で詳細構造は検証しない
- 相関チェック:
  - なし
- 業務上の入力制約:
  - メール認証はリンク到達時に自動実行し、手動送信は行わない
- 操作可能条件:
  - 認証結果が確定した後のみ遷移ボタンを表示する

## 11. API / データ要件

### 11-1. 利用 API 一覧

| 用途       | Method | Endpoint             | 入力    | 出力              | 備考                                  |
| ---------- | ------ | -------------------- | ------- | ----------------- | ------------------------------------- |
| メール認証 | POST   | `/auth/email/verify` | `token` | `message`, `user` | 認証ヘッダなし、`credentials: 'omit'` |

### 11-2. データ要件

- 画面表示に必要なデータ項目:
  - `token`
  - 認証結果メッセージ
- フロントで加工が必要な項目:
  - API エラーを状態別メッセージへ変換する
  - 成功時に `window.history.replaceState` で `token` を URL から除去する
- 欠損時のフォールバック方針:
  - `token` 欠損時は API 呼び出しを行わず欠損状態を表示する
  - 再送時は常に `/signup/email-resend` へ遷移する

## 12. UI / UX 要件

- モバイル優先で成立すること
- 600px 未満では 1 カラム、左右 16px 以上の余白で表示すること
- 600px 以上ではカード幅を拡張しても 1 カラム構成を維持すること
- 960px 以上ではカードを画面中央に置き、上下余白を十分に確保すること
- 認証中はユーザーが待機状態だと理解できる説明を明示すること
- 成功時と失敗時で次アクションが一目で分かること
- エラー時は再送を最短動線に置くこと

## 13. アクセシビリティ要件

- 見出し構造を明確にし、状態タイトルを `h1` とする
- キーボードだけで表示中の全ボタン操作を完結できる
- 状態メッセージは `aria-live="polite"` で読み上げ可能にする
- アイコンだけで意味を伝えず、必ずテキストを併記する
- コントラストは WCAG AA を満たす

## 14. 非機能要件

- 想定表示件数:
  - 一覧表示なし
- パフォーマンス上の注意:
  - 初期表示時の verify API は 1 回に抑える
  - 余分な polling や再試行ループを持たない
- 監視 / ログ出力の要件:
  - `token`、アクセストークン、パスワードをログ出力しない
  - エラーは UI 表示に必要な最小限の情報のみ扱う
- セキュリティ上の注意:
  - verify API 呼び出しでは認証ヘッダを付与しない
  - 認証成功後は URL 上に `token` を残さない
  - 登録メールアドレスは `sessionStorage` にのみ保持し、長期永続化しない

## 15. 対象外

- 認証成功後の自動ログイン
- トークン再入力 UI
- メール認証履歴の表示
- 期限切れ、既認証、再送上限などの個別説明の高度化

## 16. Definition of Done

- `pending / success / error / missing` の各状態が設計されている
- `POST /auth/email/verify` の契約と UI 表示の対応が明確である
- 成功後の URL トークン除去方針が明記されている
- 再送、再登録、ログイン、ダッシュボードへの導線が整理されている
- テスト観点が洗い出されている
