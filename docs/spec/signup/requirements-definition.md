# 会員登録画面 要件定義

## 1. 画面情報

- 画面名: 会員登録画面
- feature 名: `auth`
- route: `/signup`
- 関連画面: `/login`, `/signup/email-sent`, `/signup/email-resend`, `/signup/verify`
- ステータス: Draft
- 作成日: 2026-03-29
- 更新日: 2026-03-29

## 2. 目的とスコープ

### 2-1. 目的

- 未登録ユーザーが氏名、メールアドレス、パスワードを入力してアカウント仮登録を開始できるようにする
- 仮登録完了後に確認メール送信済み画面へ遷移し、メール認証フローへ自然に接続する

### 2-2. スコープ

- この画面で提供する機能:
  - 氏名、メールアドレス、パスワードの入力
  - クライアントサイドバリデーション
  - `POST /auth/register` による会員登録リクエスト
  - 重複メールアドレスなどの API エラー表示
  - 確認メール再送画面、ログイン画面への遷移
- この画面では扱わない機能:
  - SNS ログインや外部 ID 連携
  - プロフィール詳細設定
  - メール認証そのものの実行
  - 利用規約・プライバシーポリシー本文の表示

## 3. 対象ユーザーと利用条件

- 想定ユーザー: まだアカウントを持っていない未認証ユーザー
- 認証要件: `GuestGuard` 配下でのみ利用可能。ログイン済みユーザーは `/dashboard` にリダイレクトする
- 到達経路:
  - ログイン画面から「会員登録」導線で到達する
  - 直接 `/signup` にアクセスする
  - 確認メール再送や認証失敗画面から再登録導線で戻る

## 4. 前提条件と依存

- 関連 feature: `auth`
- 関連 API:
  - `POST /auth/register`
  - ルート表示前の認証状態確認で `useAuthSession` を利用する
- 前提データ: 初期表示時点で必須の取得データはない
- 外部サービス依存: 登録成功後の確認メール送信はバックエンド側のメール配送機構に依存する
- レイアウト制約:
  - `AuthScreenLayout` を利用する
  - モバイル優先の 1 カラム
  - `.page-shell` 内で中央寄せカード表示

## 5. ユーザーストーリー

- ユーザーとして、サービス利用を開始するために会員情報を入力して登録したい
- ユーザーとして、入力不備や登録失敗の理由をその場で把握したい
- ユーザーとして、確認メールが届かない場合に再送やログイン画面への導線へ迷わず進みたい

## 6. 画面概要

### 6-1. 画面構成

- ヘッダー: グローバルヘッダーなし。カード内にカテゴリラベル、見出し、説明文を表示する
- メインコンテンツ: 会員登録フォームカード
- 補助領域:
  - 同意事項の案内ボックス
  - API エラー表示領域
  - 確認メール再送、ログイン画面への遷移ボタン
- フッター: なし
- モーダル / ドロワー: なし

### 6-2. 主要アクション

- 初期表示時に行うこと:
  - 空のフォームを表示する
  - `GuestGuard` によりログイン済みユーザーを排除する
- ユーザー操作:
  - 氏名、メールアドレス、パスワードの入力
  - 「登録してメールを送る」の押下
  - 「確認メールを再送する」「すでに登録済みの方はこちら（ログイン）」の押下
- 操作結果:
  - 成功時は登録メールアドレスを保持して `/signup/email-sent` へ遷移する
  - 失敗時はフォーム内にエラーを表示する

## 7. ユーザーフロー

1. 未認証ユーザーが `/signup` に到達する
2. `GuestGuard` が認証状態を確認し、ログイン済みなら `/dashboard` に遷移する
3. ユーザーが氏名、メールアドレス、パスワードを入力して送信する
4. フロントエンドが入力を検証したうえで `POST /auth/register` を実行する
5. 成功時は `/signup/email-sent?email=...` へ遷移し、失敗時は画面内エラー表示に留まる

## 8. 機能要件

### 8-1. 初期表示

- 初期表示時に必要な API / データ取得:
  - 画面本体では取得しない
  - ルートガードで認証状態確認のみ行う
- 初期表示時の UI:
  - 見出し、説明文、3 項目の入力欄、同意事項案内、3 つのアクションボタンを表示する
- 権限不足 / 未認証時の扱い:
  - 未認証ユーザーは表示可能
  - ログイン済みユーザーは `/dashboard` へ遷移
  - 認証確認中はガード側で `Loading...` を表示

### 8-2. 入力 / 操作

- 入力項目:
  - 氏名
  - メールアドレス
  - パスワード
- 操作可能なボタン / リンク:
  - `登録してメールを送る`
  - `確認メールを再送する`
  - `すでに登録済みの方はこちら（ログイン）`
- 活性 / 非活性条件:
  - 通常時はすべて活性
  - 登録 API 実行中は全ボタンを非活性にする
- 二重送信防止:
  - 登録ボタンは `loading` 状態で押下不可にする

### 8-3. 出力 / 表示

- 表示内容:
  - カテゴリラベル `新規登録`
  - 見出し `会員登録`
  - 説明文
  - 同意事項プレースホルダ
  - フィールド単位のエラーメッセージ
  - API エラーメッセージ
- ラベルや補助文言:
  - ラベルは常時表示
  - プレースホルダは補助的に使用
- 表示形式:
  - メールアドレスは文字列表示
  - 日付、通貨、件数表示はなし

## 9. 状態要件

- Loading:
  - `GuestGuard` の認証確認中、および登録 API 実行中に発生する
  - 登録中はフォーム送信と画面遷移ボタンを操作不能にする
- Empty:
  - 一覧や取得データを持たないため該当なし
- Success:
  - 登録成功後は成功メッセージをこの画面内には残さず、`/signup/email-sent` に遷移する
  - 遷移時に登録メールアドレスを query parameter と `sessionStorage` に保持する
- Validation Error:
  - 入力欄直下に表示する
  - 氏名、メールアドレス、パスワードごとに独立して表示する
- API Error:
  - フォーム下部にアラート形式で表示する
  - `email_already_exists` は専用メッセージに変換する
  - それ以外は汎用エラーメッセージを表示する
- Unauthorized:
  - 画面自体はゲスト向けのため、未認証アクセス制御は不要
  - 既認証ユーザーのアクセスは `GuestGuard` で `/dashboard` に遷移する
  - 登録 API の `401` は現状 `email_already_exists` を含む業務エラーとして扱っている

## 10. バリデーションと業務ルール

- 必須項目:
  - 氏名
  - メールアドレス
  - パスワード
- フォーマット制約:
  - メールアドレスは email 形式
- 相関チェック: 現時点ではなし
- 業務上の入力制約:
  - パスワード強度ルールは未確定
  - 同意事項チェックボックスは未実装
- 操作可能条件:
  - 入力値が不正でも送信は可能だが、送信前にフォームバリデーションで停止する

## 11. API / データ要件

### 11-1. 利用 API 一覧

| 用途     | Method | Endpoint         | 入力                        | 出力                | 備考                               |
| -------- | ------ | ---------------- | --------------------------- | ------------------- | ---------------------------------- |
| 会員登録 | POST   | `/auth/register` | `{ name, email, password }` | `{ message, user }` | 成功時に確認メール送信フローへ接続 |

### 11-2. データ要件

- 画面表示に必要なデータ項目:
  - 登録フォーム入力値
  - API 応答の `user.email`
- フロントで加工が必要な項目:
  - 遷移用の `email` query parameter を URL エンコードする
  - `response.user.email` が欠損した場合は入力値のメールアドレスを使用する
- 欠損時のフォールバック方針:
  - 登録後メールアドレスは `response.user.email ?? values.email`

## 12. UI / UX 要件

- モバイル優先で成立すること
- 600px / 960px で表示幅を広げても 1 カラムを維持すること
- 主要 CTA の `登録してメールを送る` をフォーム末尾に固定の順序で配置すること
- エラー発生時も入力値を保持し、再入力コストを増やさないこと
- 確認メール再送とログインへの導線を同じカード内で視認できること

## 13. アクセシビリティ要件

- ラベルは常時表示し、入力要素に関連付ける
- キーボードだけで入力から送信まで完結できる
- フォーカス順は氏名、メールアドレス、パスワード、送信、再送、ログインの順で自然につながる
- 入力エラーは各入力直下に表示し、`aria-describedby` で関連付ける
- API エラーは `role="alert"` と `aria-live="polite"` で読み上げ可能にする

## 14. 非機能要件

- 想定表示件数: 一覧表示なし
- パフォーマンス上の注意:
  - 初期表示時に追加データ取得を持たない軽量画面とする
  - 二重送信を防ぎ不要な登録 API 呼び出しを避ける
- 監視 / ログ出力の要件:
  - 画面内での追加ログ出力は持たない
- セキュリティ上の注意:
  - パスワード入力は `type="password"` を使用する
  - パスワード値を永続化しない
  - 保持するのはメールアドレスのみで、`sessionStorage` に限定する

## 15. 対象外

- 利用規約同意の厳密な業務ロジック
- パスワード再設定導線
- CAPTCHA や bot 対策
- 会員登録後のプロフィール入力や初期セットアップ

## 16. Definition of Done

- 未認証ユーザーが会員登録を完了して確認メール送信済み画面へ遷移できる
- フィールド単位のバリデーションと API エラー表示が成立する
- ログイン済みユーザーのアクセス制御が考慮されている
- 登録成功後のメールアドレス保持方針が明確になっている
- テスト観点が洗い出されている

## 17. 未解決事項

- 利用規約・プライバシーポリシー同意を必須化するか未確定
- パスワードの最小文字数や複雑性ルールが未確定
- `email_already_exists` を `401` で返す API 契約を継続するか要確認
- `GuestGuard` の `Loading...` 表示を認証画面向けの見た目に寄せるか未確定
