# ダッシュボード画面 要件定義

本書はダッシュボード画面の要件を定義する。実装方針は [basic-design.md](./basic-design.md) を参照する。

## 1. 画面情報

- 画面名: ダッシュボード画面
- feature 名: `dashboard`
- route: `/dashboard`
- 関連画面: `/login`, `/billing-summary`, `/manual-mail-workflows`
- ステータス: draft
- 作成日: 2026-04-10
- 更新日: 2026-04-10

## 2. 目的とスコープ

### 2-1. 目的

- 認証済みユーザーがログイン後の起点画面として、現在の解析状況と請求保存状況をすぐ把握できるようにする
- 次に利用する主要機能である請求集計画面と手動メール取得画面への導線を提供する

### 2-2. スコープ

- この画面で提供する機能:
  - 3 KPI の表示
  - 補完件数の補助説明 tooltip の表示
  - 請求集計画面への導線
  - 手動メール取得画面への導線
  - 初期取得、API エラー、認証切れを考慮した画面状態設計
- この画面では扱わない機能:
  - 月次推移や詳細内訳の表示
  - KPI の期間切替やフィルタ
  - データの編集、削除、再集計
  - 補完件数の今月値と累計値の両方表示

## 3. 対象ユーザーと利用条件

- 想定ユーザー:
  - ログイン済みの一般ユーザー
  - 解析結果と保存状況を起点画面で確認したい運用担当者
- 認証要件:
  - `AuthGuard` 配下の保護画面として利用する
  - 未認証ユーザーは直接利用できない
- 到達経路:
  - `/login` の認証完了後
  - ヘッダーのアプリ名クリック
  - URL 直接入力

## 4. 前提条件と依存

- 関連 feature:
  - `dashboard`
  - `auth`
  - `billing`
  - `manual-mail-workflows`
- 関連 API:
  - `GET /dashboard/summary`
  - `GET /auth/check`（guard で利用）
- 前提データ:
  - dashboard summary が次の 3 項目を返す
    - `current_month_analysis_success_count`
    - `current_month_fallback_billing_count`
    - `total_saved_billing_count`
  - 各値は 0 以上の整数である
- 外部サービス依存:
  - なし
- レイアウト制約:
  - `DashboardLayout` 配下で表示する
  - モバイル優先、白ベース + 緑アクセントを維持する

## 5. ユーザーストーリー

- ユーザーとして、今月の解析状況を確認するために、起点画面ですぐ件数を見たい
- ユーザーとして、今月どの程度 fallback が発生しているかを確認するために、補完件数を見たい
- ユーザーとして、これまで保存された請求件数を把握するために、累計保存件数を見たい
- ユーザーとして、必要に応じて請求集計または手動メール取得へすぐ遷移したい

## 6. 画面概要

### 6-1. 画面構成

- ヘッダー:
  - `DashboardLayout` のグローバルヘッダー
- メインコンテンツ:
  - 画面タイトル
  - 説明文
  - KPI セクション
  - 請求集計導線カード
  - 手動メール取得導線カード
- 補助領域:
  - 補完件数の説明 tooltip
  - API エラー時の再試行領域
- フッター:
  - `DashboardLayout` のグローバルフッター
- モーダル / ドロワー:
  - なし

### 6-2. 主要アクション

- 初期表示時に行うこと:
  - dashboard summary を取得する
  - 取得結果から 3 KPI を表示する
- ユーザー操作:
  - 補完件数の説明 tooltip を開閉する
  - 請求集計へ遷移する
  - 手動メール取得へ遷移する
  - API エラー時に再試行する
- 操作結果:
  - 補完件数の意味を補助的に確認できる
  - 関連画面へ遷移できる
  - 認証切れ時はログイン画面へ戻る

## 7. ユーザーフロー

1. ユーザーが `/dashboard` に到達する
2. `AuthGuard` が認証状態を確認する
3. 認証済みであれば dashboard summary を取得する
4. 取得成功時は 3 KPI と導線カードを表示する
5. ユーザーは補完件数 tooltip を開くか、関連画面へ遷移する
6. 取得失敗時は再試行導線を表示する
7. `401` 発生時は `/login` へ戻る

## 8. 機能要件

### 8-1. 初期表示

- 初期表示時に必要な API / データ取得:
  - `GET /dashboard/summary`
- 初期表示時の UI:
  - 見出し `解析・保存サマリー`
  - 説明文
  - 3 KPI
    - `今月の解析成功件数`
    - `今月の補完件数`
    - `累計保存請求件数`
  - 請求集計導線
  - 手動メール取得導線
- 権限不足 / 未認証時の扱い:
  - route 到達前は `AuthGuard` で `/login` へ遷移する
  - 画面表示後に API が `401` を返した場合も `/login` へ戻す

### 8-2. 入力 / 操作

- 入力項目:
  - フォーム入力は持たない
- 操作可能なボタン / リンク:
  - `今月の補完件数の説明を表示`
  - `請求集計を開く`
  - `手動メール取得を開く`
  - `再試行`
- 活性 / 非活性条件:
  - 成功時は補完件数 tooltip と導線リンクを操作可能とする
  - loading 中は KPI 本文以外の画面骨格は表示してよい
  - エラー時は再試行操作を許容する
- 二重送信防止:
  - mutation は存在しない
  - query は TanStack Query により同一 key の重複取得を抑制する

### 8-3. 出力 / 表示

- KPI の表示順:
  - `今月の解析成功件数`
  - `今月の補完件数`
  - `累計保存請求件数`
- KPI の補助説明:
  - 補完件数は「請求日がメールに無いため、メール受信日で判定した件数」
- 表示形式:
  - 件数は千区切り付き整数で表示する
  - 単位は `件` とする
  - `0` は正常値として表示する

## 9. 状態要件

- Loading:
  - 初回取得中は KPI セクション内に loading 表示を出せる
  - 関連画面への導線は画面骨格として維持してよい
- Empty:
  - 独立状態は持たない
  - 3 KPI がすべて `0` の場合も success として扱う
- Success:
  - 3 KPI と導線カードを表示する
  - 成功メッセージは不要
- Validation Error:
  - フォーム入力がないため該当なし
- API Error:
  - KPI セクション内にエラー表示と再試行導線を表示する
- Unauthorized:
  - `401` 時は認証情報を破棄し、`/login` へ遷移する

## 10. バリデーションと業務ルール

- 必須項目:
  - なし
- フォーマット制約:
  - 3 KPI は 0 以上の整数である
- 相関チェック:
  - なし
- 業務上の入力制約:
  - なし
- 操作可能条件:
  - KPI 表示順は固定し、API の返却順には依存しない

## 11. API / データ要件

### 11-1. 利用 API 一覧

| 用途         | Method | Endpoint             | 入力 | 出力 | 備考 |
| ------------ | ------ | -------------------- | ---- | ---- | ---- |
| KPI 初期取得 | GET    | `/dashboard/summary` | なし | `current_month_analysis_success_count`, `current_month_fallback_billing_count`, `total_saved_billing_count` | 認証必須 |

### 11-2. データ要件

- 画面表示に必要なデータ項目:
  - `current_month_analysis_success_count`
  - `current_month_fallback_billing_count`
  - `total_saved_billing_count`
- フロントで加工が必要な項目:
  - 千区切り整形
  - 単位 `件` の付与
- 欠損時のフォールバック方針:
  - 欠損は許容せず、API は `0` を返す前提とする

## 12. UI / UX 要件

- モバイル優先で成立すること
- KPI はファーストビューで視認できること
- KPI は 1 つのサマリーセクション内で整理し、過度にネストしたカード構造にしないこと
- 導線カードは KPI より下に並べ、主従関係を明確にすること
- 600px / 960px での表示差分に対応すること

## 13. アクセシビリティ要件

- 補完件数 tooltip ボタンに説明用ラベルを付与する
- キーボードだけで補完件数 tooltip と導線操作を完結できる
- フォーカス順が自然である
- tooltip は `role="tooltip"` を持ち、説明対象と関連付く
- コントラストは WCAG AA を満たす

## 14. 非機能要件

- 想定表示件数:
  - KPI 3 件、導線 2 件
- パフォーマンス上の注意:
  - 初期表示向けの軽量なレスポンスにする
- 監視 / ログ出力の要件:
  - API エラーは原因追跡可能な形で扱えること
- セキュリティ上の注意:
  - KPI 以外の秘匿情報を画面に出さない
  - 認証切れ時は保護画面として復帰させない

## 15. 対象外

- 請求推移グラフや支払先別内訳の表示
- provider 単位、connection 単位の breakdown
- KPI の CSV 出力
- ダッシュボード上での再解析や再取得操作

## 16. Definition of Done

- 3 KPI と主要導線の要件が定義されている
- Loading / Success / Error / Unauthorized が整理されている
- API 契約と表示項目の対応が明確である
- KPI の意味と表示順が明確である
- 補完件数 tooltip と導線のアクセシビリティ要件が整理されている
