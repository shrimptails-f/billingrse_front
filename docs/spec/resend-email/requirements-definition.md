# メール再送信画面 要件定義

## 1. 画面情報

- 画面名: メール再送信画面
- feature 名: `auth`
- route: `/signup/email-resend`
- 関連画面: `/signup`, `/signup/email-sent`, `/signup/verify`, `/login`
- 作成日: 2026-03-29
- 更新日: 2026-03-29

## 2. 目的とスコープ

### 2-1. 目的

- 会員登録後に確認メールが届かない、または認証に失敗したユーザーが、自分で確認メールを再送できるようにする
- 再送結果を同一画面で明示し、次に取るべき行動を迷わず選べるようにする

### 2-2. スコープ

- この画面で提供する機能:
  - メールアドレスとパスワードの入力
  - query parameter または `sessionStorage` からのメールアドレス初期表示
  - クライアントサイドバリデーション
  - `POST /auth/email/resend` による確認メール再送
  - 成功 / 失敗 / 既認証済みの結果表示
  - ログイン画面への導線表示
- この画面では扱わない機能:
  - 会員登録そのものの実行
  - メール認証リンクの実行
  - パスワード再設定
  - 再送回数制限や待機時間の詳細表示

## 3. 対象ユーザーと利用条件

- 想定ユーザー:
  - 会員登録後に確認メールが届いていない未認証ユーザー
  - `/signup/verify` で認証失敗となり再送が必要なユーザー
  - 会員登録済みメールアドレスを保持しており、再送だけをやり直したいユーザー
- 認証要件:
  - 画面自体は未ログインで利用可能とする
  - API 呼び出し時は認証ヘッダや既存セッションを前提にしない
- 到達経路:
  - `/signup`
  - `/signup/email-sent`
  - `/signup/verify`
  - URL 直接入力

## 4. 前提条件と依存

- 関連 feature:
  - `auth`
- 関連 API:
  - `POST /auth/email/resend`
- 前提データ:
  - `email` query parameter は任意
  - `sessionStorage.lastRegisteredEmail` をメールアドレス候補として利用できる
- 外部サービス依存:
  - 確認メール配信基盤
- レイアウト制約:
  - `AuthScreenLayout` を使った認証系の共通レイアウト
  - モバイル優先の 1 カラム構成
  - 白ベース、緑アクセント、中央寄せカード

## 5. ユーザーストーリー

- ユーザーとして、確認メールが届かないときに、会員登録し直さず再送したい
- ユーザーとして、前画面で入力したメールアドレスを再入力せずに再送したい
- ユーザーとして、再送の成否や既認証済みかどうかを画面上で把握したい

## 6. 画面概要

### 6-1. 画面構成

- ヘッダー:
  - グローバルヘッダーは表示しない
  - カード内にカテゴリラベル、タイトル、説明文を表示する
- メインコンテンツ:
  - 補助案内ボックス
  - メールアドレス入力
  - パスワード入力
  - 再送結果のフィードバック領域
  - 再送ボタン、ログイン画面遷移ボタン
- 補助領域:
  - 背景グラデーション
  - `.page-shell` による左右余白と中央寄せ
- フッター:
  - なし
- モーダル / ドロワー:
  - なし

### 6-2. 主要アクション

- 初期表示時に行うこと:
  - `email` query parameter を確認する
  - query がなければ `sessionStorage.lastRegisteredEmail` を参照する
  - 取得できたメールアドレスを入力欄初期値として表示する
- ユーザー操作:
  - メールアドレスとパスワードを入力する
  - `確認メールを再送する` を押下する
  - `ログイン画面へ戻る` を押下する
- 操作結果:
  - 成功時は成功メッセージを画面内に表示し、入力したメールアドレスを保持する
  - 失敗時は同画面内でエラー内容を表示する
  - 既認証済みの場合は情報メッセージを表示する

## 7. ユーザーフロー

1. ユーザーが `/signup/email-resend` に到達する
2. 画面は query parameter と `sessionStorage` からメールアドレス候補を解決し、フォームを表示する
3. ユーザーがメールアドレスとパスワードを入力して再送を実行する
4. フロントエンドが入力を検証したうえで `POST /auth/email/resend` を実行する
5. 成功時は成功メッセージを表示し、メールアドレスを `sessionStorage` に保持する
6. 失敗時はエラーまたは情報メッセージを表示し、入力内容の修正や再送を可能にする
7. ユーザーは必要に応じてログイン画面へ戻る

## 8. 機能要件

### 8-1. 初期表示

- 初期表示時に必要な API / データ取得:
  - 初期表示専用の API 呼び出しは行わない
  - `email` query parameter と `sessionStorage.lastRegisteredEmail` を参照する
- 初期表示時の UI:
  - カテゴリラベル `確認メールの再送`
  - 見出し `確認メールをもう一度送る`
  - 説明文
  - 補助案内ボックス
  - メールアドレス入力
  - パスワード入力
  - `確認メールを再送する`
  - `ログイン画面へ戻る`
- 権限不足 / 未認証時の扱い:
  - 公開画面として表示を許容する
  - 未認証アクセスでもログイン画面へは遷移可能とする

### 8-2. 入力 / 操作

- 入力項目:
  - メールアドレス
  - パスワード
- 操作可能なボタン / リンク:
  - `確認メールを再送する`
  - `ログイン画面へ戻る`
- 活性 / 非活性条件:
  - 通常時は両ボタン活性
  - 再送 API 実行中は両ボタン非活性
- 二重送信防止:
  - mutation 実行中は再送ボタンをローディング表示にし、再送信を防止する

### 8-3. 出力 / 表示

- 入力欄ラベルは常時表示する
- バリデーションエラーは各入力欄の直下に表示する
- 再送結果はフォーム内フィードバック領域に表示する
- フィードバックの表示方針:
  - 成功時は緑系
  - エラー時は赤系
  - 既認証済みは青系の情報表示
- ボタン文言:
  - 通常時: `確認メールを再送する`
  - 送信中: `送信中...`

## 9. 状態要件

- Loading:
  - 再送 API 実行中に表示する
  - 再送ボタンをローディング表示にする
  - 再送、ログイン遷移の両操作を不能にする
- Empty:
  - 一覧や取得データの empty 状態は存在しない
  - 初期状態は空またはメールアドレス初期値入りフォーム表示とする
- Success:
  - API の `message` を成功メッセージとして表示する
  - 画面遷移は行わず、同画面で結果を確認できるようにする
  - 入力したメールアドレスを `sessionStorage` に保持する
- Info:
  - `already_verified` の場合は情報メッセージを表示する
  - エラーとして扱わず、状況説明に留める
- Validation Error:
  - 各入力欄の直下に表示する
  - 送信は実行しない
- API Error:
  - フォーム内フィードバック領域に表示する
  - `invalid_credentials` は専用メッセージに変換する
  - それ以外は API の `message` または汎用メッセージを表示する
- Unauthorized:
  - `401` はログイン画面へリダイレクトせず、資格情報エラーとして画面内表示する

## 10. バリデーションと業務ルール

- 必須項目:
  - メールアドレス
  - パスワード
- フォーマット制約:
  - メールアドレスは email 形式
- 相関チェック:
  - なし
- 業務上の入力制約:
  - パスワード強度判定は行わない
  - メールアドレス初期値は `email` query parameter を優先し、なければ `sessionStorage` を使う
- 操作可能条件:
  - API 実行中以外は再送可能

## 11. API / データ要件

### 11-1. 利用 API 一覧

| 用途             | Method | Endpoint             | 入力                | 出力      | 備考                     |
| ---------------- | ------ | -------------------- | ------------------- | --------- | ------------------------ |
| 確認メール再送信 | POST   | `/auth/email/resend` | `email`, `password` | `message` | 認証ヘッダなしで実行する |

### 11-2. データ要件

- 画面表示に必要なデータ項目:
  - メールアドレス
  - パスワード
  - フィードバックメッセージ
- フロントで加工が必要な項目:
  - query parameter の `email` をフォーム初期値へ反映する
  - `email` query parameter を `sessionStorage` に同期する
  - 成功時に送信したメールアドレスを `sessionStorage` に保存する
- 欠損時のフォールバック方針:
  - `email` query も `sessionStorage` もない場合は空のメールアドレス入力欄から開始する

## 12. UI / UX 要件

- モバイル優先で成立すること
- 600px 未満では 1 カラム、左右 16px 以上の余白で表示すること
- 600px 以上ではカード幅を拡張しても 1 カラム構成を維持すること
- 960px 以上では上下余白を十分に確保し、カードを画面中央に配置すること
- 補助案内により、迷惑メールフォルダ確認を促すこと
- 再送結果がフォーム近傍で即時に分かること

## 13. アクセシビリティ要件

- ラベルは常時表示し、入力要素と関連付ける
- キーボードだけで入力、送信、ログイン遷移を完結できる
- フォーカス順はメールアドレス、パスワード、再送、ログインの順で自然につながる
- 入力エラーは各入力直下に表示し、`aria-describedby` で関連付ける
- フィードバック領域は `aria-live="polite"` で読み上げ可能にする
- コントラストは WCAG AA を満たす

## 14. 非機能要件

- 想定表示件数:
  - 一覧表示なし
- パフォーマンス上の注意:
  - 初期表示時に追加の API 呼び出しを持たない
  - 二重送信を防ぎ、不要な再送 API 呼び出しを避ける
- 監視 / ログ出力の要件:
  - 追加の画面ログ出力は持たない
- セキュリティ上の注意:
  - パスワード入力は `type="password"` を使用する
  - パスワード値を永続化しない
  - `sessionStorage` に保持するのはメールアドレスのみとする

## 15. 対象外

- パスワード再発行導線
- 会員登録フォームの再表示
- 再送回数制限の詳細説明
- メール認証リンクの結果画面の設計見直し

## 16. Definition of Done

- 未認証ユーザーが確認メールを再送できる
- メールアドレス初期値の解決方針が明確である
- Loading / Success / Info / Validation Error / API Error を設計済みである
- API 契約とフィードバック表示の対応が明確である
- テスト観点が洗い出されている
